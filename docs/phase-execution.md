# Evidence-gated project phases

AUTO/Supervisor tasks follow one execution path:

User goal → Supervisor project plan → selected workers → phase gate → durable
checkpoint → next phase → authoritative final acceptance.

The planner proposes scope; the runtime owns advancement and completion. The
Supervisor has no tools. Plans cannot add capabilities, executable commands,
packages, approved origins, or filesystem access. The existing Broker, Policy
Engine, human approval, workspace confinement, Docker adapters, and browser/Web
network restrictions remain in force.

## Models and lifecycle

`ProjectPlan` contains a bounded summary, 1–12 ordered `PhasePlan` entries and
at most three controlled Web requests. Substantial projects normally need 3–8
phases. Phase IDs are unique lowercase identifiers; dependencies may refer only
to earlier phases. Each phase selects registered workers from researcher, coder,
reviewer, executed in that order. Invalid plans fail before worker execution.

A phase has a small goal, existing `AcceptanceCriteria`, optional deterministic
verification (`environment`, `build`, `test`, `visual_qa`), and either the normal
worker workflow or the existing visual workflow. Required operator research
gets a research stage before implementation. Missing required Web evidence fails
closed unless the operator explicitly permits degraded research. Final operator
acceptance is merged into the last phase and checked again at task completion.

Worker `finish` requests verification of the current phase. Missing files,
incomplete/stale readback, failed tests/builds, unavailable environments, missing
QA/review or required research reject completion. Outstanding evidence and compact
diagnostics go to a fresh invocation in the same phase. Review FAIL cannot be
cleared by another model verdict without observed source changes. Default repair
attempts are bounded; even Unlimited stalls after three identical phase failures.
Visual phases retain the existing real-repair counting and no-progress limits.

Statuses distinguish pending, running, waiting_for_approval, verifying, passed,
failed, stalled and paused. Worker failures feed phase diagnostics; failed phases
retain earlier checkpoints. Toolchain failures retain their original diagnostic,
including infrastructure failures. Final COMPLETED requires every phase passed,
no pending approval, and accepted authoritative evidence. Model claims are not
evidence and cannot produce a green task with rejected acceptance.

## Pocket Ledger example

An operator selects the confined `pocket-ledger` Flask project and its final
acceptance requirements. A suitable five-phase plan is:

| Phase | Workers | Exit evidence |
| --- | --- | --- |
| environment | Coder | `project.json` exists/read back; approved dependencies; environment READY |
| backend | Coder | `app.py` and backend tests exist/read back; CRUD and validation tested |
| frontend | Coder → Reviewer | templates/assets exist/read back; source review PASS |
| verification | Coder | deterministic `project.build` and `project.test` pass |
| final-qa | Reviewer; Coder only for repair | rendered route screenshots/report and final Reviewer PASS |

For example, the verification phase can be represented as:

```json
{
  "id": "verification",
  "title": "Run backend tests and build assets",
  "goal": "Repair failing validation tests and verify the existing frontend build.",
  "workers": ["coder"],
  "depends_on": ["frontend"],
  "requirements": {
    "required_files": ["pocket-ledger/tests/test_app.py"],
    "required_read_after_write": ["pocket-ledger/tests/test_app.py"]
  },
  "verification": ["build", "test"],
  "workflow": "workers"
}
```

This is an illustrative plan, not a claim that Pocket Ledger was generated by
the test suite. Tests drive real orchestration with scripted model responses.

## Compact context and structured tools

Each worker invocation receives the concise overall summary, current phase goal,
verified prior checkpoint summaries, current responsibilities, requirements,
security constraints and bounded current diagnostics. It does not receive the
original large user prompt or all historical worker transcripts again. Same-phase
peer findings are explicitly untrusted claims. Fixed truncation bounds keep the
context bounded; the audit trail remains available independently.

Structured output uses an object envelope with a `decision` union. Each branch
binds one tool name to that tool's own argument schema. Legacy flat decisions
remain parseable; both forms still undergo Broker validation and policy checks.
Legacy one-paragraph plans migrate into a single phase in this same engine.

## Persistence, approvals and resume

The existing task SQLite record stores JSON `project_plan` and `phase_execution`:
ordered phases/current index, attempts, worker results, evidence summaries,
changed files and hashes, pending approval IDs, progress timestamps, visual
workflow checkpoints and stop reasons. Checkpoints update throughout execution.

After restart, passed phases remain passed and interrupted execution becomes
PAUSED. Operator resume starts fresh invocations at the first unfinished phase;
it does not replay in-flight model calls or automatically reapprove actions.
Fresh file hashes and environment inspection invalidate the earliest affected
checkpoint and its successors when necessary. Other passed workers are not rerun.
Resolved approval state is supplied as diagnostic context; unresolved approvals
block resume. Failed phased tasks can be explicitly resumed without replanning.

An unchanged dependency manifest that already failed returns
`DEPENDENCY_RETRY_NOT_PROGRESS`, retaining the existing request and actual error.
The worker must correct the manifest. Only an authenticated operator may retry
the same request for a recorded retryable infrastructure condition (Docker
readiness or timeout); this does not bypass package or digest checks.

## Observability and dashboard

Context-local metadata automatically annotates nested events and JSON logs with
`phase_id`, one-based `phase_index`, `phase_title`, `phase_attempt`, and
`phase_count`. Operator approval events recover the requesting phase from its
audit record. Task context cannot leak into another task's events.

Lifecycle events cover planning, start, worker start, verification, rejected
completion, repair, pass, failure, stall, pause and resume. The dashboard displays
the structured phase plan, active phase, requirements, verification status,
attempts, outstanding findings, changed files and pending approvals. Live rows
carry phase badges; failed/paused/stalled tasks identify the phase visibly.
Existing task/visual workflow panels and tasks without phase state still render.

## Limits

- Recovery is explicit, single-process orchestration; there is no durable job
  queue, automatic restart scheduler, or restoration of in-flight model calls.
- Hash revalidation covers recorded/required files. It is not a whole-workspace
  transactional snapshot and cannot prove semantic correctness or prevent all
  concurrent operator edits. External infrastructure can change after a check.
- Planning quality and semantic review depend on the model. Runtime checks prove
  recorded execution/evidence, not that an application meets every prose goal.
- Visual QA uses the existing deterministic routes/viewports; pixel inspection
  requires a vision-enabled model. Screenshot generation alone is not a claim
  that a text-only Reviewer saw image pixels.
- Provider-shaped schemas are tested offline; this change does not certify every
  live model/provider combination or perform a live Pocket Ledger generation.
